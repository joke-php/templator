# Безопасность шаблонов

## Назначение

Шаблонизатор закрывает две типовые веб-уязвимости на уровне синтаксиса — XSS (автоматическим экранированием) и CSRF (
директивой `{% csrf %}`) — но обе защиты можно свести на нет неосторожным использованием `{% raw %}` или неверной
передачей данных в контекст. Ниже — что делает движок сам, и что остаётся на разработчике.

## Автоматическое экранирование (XSS)

`{{ выражение }}` всегда компилируется в `htmlspecialchars((string)$значение, ENT_QUOTES, $encoding)` — без исключений и
без возможности отключить это для конкретного `{{ }}`. Заменяются все пять спецсимволов: `&` → `&amp;`, `<` → `&lt;`,
`>` → `&gt;`, `"` → `&quot;`, `'` → `&#039;`. Это первая и главная линия защиты: любые данные, включая пользовательский
ввод, безопасно попадают в HTML, если вы используете `{{ }}` по умолчанию для всего.

## Опасности использования {% raw %}

`{% raw путь %}` выводит значение без какой-либо обработки — если путь ведёт к данным, которые прямо или косвенно пришли
от пользователя, это прямая XSS-уязвимость.

```php
// УЯЗВИМО: комментарий пользователя выводится как есть
$response->show('pages/post.php', ['comment' => $request->post('comment')]);
```

```html
{% raw comment %} <!-- браузер выполнит любой <script> из комментария -->
```

```php
// БЕЗОПАСНО: raw — только для контента, прошедшего санитизацию на сервере
$response->show('pages/post.php', ['bodyHtml' => $htmlPurifier->purify($rawBody)]);
```

```html
{% raw bodyHtml %}
```

Строгое правило: `{% raw %}` — только для HTML, который приложение либо сгенерировало само, либо пропустило через
санитайзер.
Подробнее — [Вывод данных](04-directives/03-print-and-raw.md).

## Защита от CSRF-атак

Каждая форма с методом, отличным от `GET`/`HEAD`, обязана содержать поле `csrf_token` со значением `{% csrf %}`:

```html

<form method="post" action="/profile/update">
    <input type="hidden" name="csrf_token" value="{% csrf %}">
</form>
```

Это работает только на маршрутах, обёрнутых в `CsrfMiddleware` — по умолчанию это группа `web` (`routes/web.php`). На
маршрутах без этого middleware токен сгенерируется, но проверяться не будет.
Детали — [Директива csrf](04-directives/07-csrf.md).

## Потенциальные риски точечной нотации

Точечная нотация (`user.profile.name`) в этом шаблонизаторе — **только доступ к ключам массива**, вызов методов
объекта (`{{ user.delete }}` как вызов `$user->delete()`) невозможен архитектурно: `compileVarAccess()`/`resolveValue()`
умеют исключительно `$context['user']['delete']`. Реальный риск другого рода — **избыточная передача данных**: если в
контекст попадает весь массив модели целиком (включая хеш пароля, внутренние токены, служебные поля), любой ключ
становится доступен любому автору шаблона через точечный путь. Передавайте в шаблоны заранее собранные DTO/массивы
только с нужными полями, а не сырой дамп сущности из БД.

## Чеклист безопасности перед релизом

- [ ] Все пользовательские данные выводятся через `{{ }}`
- [ ] `{% raw %}` используется минимально и обоснованно
- [ ] Все формы защищены `{% csrf %}`, маршрут в группе `web`
- [ ] В `$context` передаются только отобранные поля (DTO/массивы), а не целые модели
